### UI 架构整理：设计规范与资产归属（2026-11-22）

按 ZCode v3.18.2 的前端架构对照（研究原文在 `docs/research/`，不入库），决定：

- `design-system` 保持独立包，不学 ZCode 把设计系统、应用装配与 RPC 依赖塞进同一个包。
- 新增 `packages/design-system/DESIGN.md` 作为界面使用规范：只写语义与边界，数值仍只在 `tokens/`。
- 新增 `docs/design/` 记录已拍板的设计规则与 UI 资产归属表。
- 功能 CSS 只做布局；层归属与层序见下面「项目 CSS 全量迁入层」。
- 补齐 DS 缺口：`Input` / `Textarea` / `Checkbox` / `Radio` / `RowButton`；
  替换时按 L1/L2 对拍，不追求一次覆盖全部原生控件。
- `style-boundaries` 增 S11：引用未定义的 `--ui-*` / `--cp-*` 记红（两道已知缺陷与
  `--cp-rail-card-y` 运行时变量登记为例外），防止声明静默失效再漏过去。
- 样板：automations（第二块 review，参照 agent-settings）；每批只做一类事，
  `bun run all` 绿才提交。
- 明确不做：拆 `assistant.css` 的业务耦合、换 CVA、搬 ZCode 的 2360 行 policy YAML。

### 项目 CSS 全量迁入层（2026-11-22）

按用户裁决做一次性完整迁移，不逐功能 L2：

- 层序在 `apps/desktop/src/renderer/styles.css` 声明：
  `theme < base < vendor.xterm < components.ds < components.kit < components.workbench < components.features < utilities < overrides < prose`。
  DS 组件 17 份、conversation-kit 6 份、workbench 5 份、功能 65 份全部进各自子层。
- 第三方 CSS（xterm）进 `vendor.xterm`：它无层时会压过功能 CSS，终端面板对 `.xterm-viewport`
  的透明底色覆盖就会失效（四周露黑）。
- `overrides` 层在 `utilities` 之后：收主题相关、必须盖过工具类的组件皮肤

  `control/menu.css` 保持无层，文件头既有意图是「行样式要压过工具类」，登记为永久例外。

  不加载。`@import` 已移回层外；这是位置敏感指令，后续迁移不得再包。

### 定时任务对齐 ZCode 调度模型（2026-11-22）

按用户裁决「只对齐定时自动化、行为等价重写」移植 ZCode 的派发台账（ZCode v3.18.2 的
`automationRepo` / `desktop/src/scheduler`）。已落地：schema v2（`claimed_at`、`dispatch_*`、`retry_at`、
`last_error`、`run_count`，运行行补 `dispatch_status` / `attempts`）、SQLite 事务内原子认领与 10 分钟僵尸回收、
`<automationId>:<scheduledFor>` 幂等运行键、派发失败 30s→15min 封顶 5 次退避、一次性任务错过即终态、
全库 20 条创建上限。schema v3 再加 `schedule_rule`（JSON）、`max_runs`、`end_at`：自定义重复以规则为唯一调度事实，
`cron` 只做兼容展示；达到次数上限或下一次超过截止即停用。agent 工具补了 `intervalUnit`+`interval`、
`recurring`/`maxRuns`/`endAt` 与 `automation_pause_self`。协议形状变化已升 `PROTOCOL_VERSION` 到 78 并重生成快照。

与 ZCode 的差异（保留 Poietica 现状，不照抄）：

- **调度器宿主**：ZCode 用 `electronUtilityProcess.fork` 拉起独立 cron 进程，因为它的 Main 必须保持薄。
  Poietica 的 Core 已是唯一长驻、唯一的库写者，调度器放 `features/automations/core` 即可；多一个进程只会多一套消息协议。
- **错过窗口**：ZCode 默认跳过（misfire grace 后记 skipped）。Poietica 保留每任务的 `catchUp` 选项与
  「应用没开着」文案，只把**一次性任务**改成错过即终态，不再从兼容 cron 推导下一次。
- **立即运行**：ZCode 把 manual run 写进 `automation_runs` 排队，避免与 scheduler 的派发并发；Poietica 的 Core
  在写运行行与提交之间没有可穿插的进程，`runNow` 仍直接派发，靠 open run 拒绝重复触发。
- **编辑器的规则保真**：编辑器新增「自定义间隔」入口（用户 2026-11-22 裁决，属有意的视觉变更），规则直接进草稿；
  服务端按规则写兼容 cron，cron 只作展示。旧版存盘只带 cron/at/时区时，服务层按「三格没变就保留原规则、改了计划才清掉」处理。
- **派发失败可见**：列表卡片与编辑器提示写 `lastError` 与 `retryAt`（重试中 / 最终失败分开），工具卡状态同步读 `dispatchStatus`。

产品要求用一组 CSS 开关打磨换行、空格、对齐与截断。这是一次**有意的视觉变更**，与「界面视觉不得擅自改动」的常规约束不同，按任务要求执行；字体、字色、字号与布局宽度令牌未改。

### runtime 入口漏了 omp 的 worker 分派（2026-11-17）

拆分出 `poietica-runtime.exe`（41a919ca）时，`dispatchProcessMode` 留在 `apps/core/src/main.ts` 里跟 `serve` 一起，
而新入口 `runtime-entry.ts` 只认 `gc` 与 runtime 主模式。omp 里所有 worker 线程与 IPC 子进程都靠
`workerHostEntry()`（编译版 = `Bun.main`）重新进入这个 exe，argv[2] 是选择子——于是 eval 的隔离子进程一开就被
`runtime-main` 的「缺少 --data-root」判成退出码 2，surface 成 `Failed to initialize isolated JS eval worker:
JS eval worker exited`；回落的 Bun Worker 走同一条入口，一样死，所以 JS / Python 两条语言通道全灭。
`computer` 不是顶层工具、只经 eval prelude 注入（`packages/omp-types/src/tools.ts`），因此跟着整块不可用。

- **偏差**：把分派拆成两半——纯判据 `classifyChildMode` + `dispatchChildMode`（交回 omp，主入口接着走自己的模式），
  `dispatchProcessMode` 保留给 serve 入口，先调 `dispatchChildMode` 再认 `serve`。这样两个入口共用一条判据，
  不会一处改了另一处忘。
- **顺序**：`runtime-entry` 里 `captureLaunchEnv()` → `dispatchChildMode()` → 动态 `import('./runtime-main')`。
  快照必须在 worker 之前（worker 要拿到同一份清洗后的环境），分派必须在 runtime 主模式之前且早于第一个 await 之外的副作用。
- **钉住**：`bootstrap/__tests__/child-mode-routing.test.ts`（判据真值表）、`apps/core/src/__tests__/runtime-entry.test.ts`
  （源码顺序：先 dispatch 再 import runtime-main、快照先于 dispatch）。
- **证据**：探针版 exe 上以 advanced IPC 发 `init`，95ms 收到 `ready`；ARP 走完 hello → freezeTools → 开会话 → 读空页 →
  关会话；`gc` 维护子进程退出码 0。

### 流式热路径只碰被覆盖的格子（2026-11-15）

「聊得越久每一批越贵」的根因不在 React，在 fold 之后那一步：`materialize` 把覆盖层压到已提交层时逐一走遍**全部**条目 / 段 / 帧，只为把没被覆盖的交回原引用。结果等价，代价是 O(全部帧)，且每条流式增量都付一遍（600 轮、约 4800 帧的对话上每批 0.19–0.24ms，其中一半花在这趟全表；300 批合计 90–110ms，全部落在渲染进程主线程上）。

- **改法**：覆盖层只认几个 `frameId`，按「帧号 → (条目, 段, 帧) 位置」的 WeakMap 直达（`committed` 换新对象时才重建，而流式增量只换覆盖层），只复制被改写的那几个 turn / step，其余位置保留原引用。语义不变 —— 仍返回新的 `AgentState`，`items` 数组仍是新数组（下游按引用记账的缓存照旧命中），只有「没被改到的条目 / 段」少了一次遍历与一次浅拷贝。
- **顺带**：`stdout` 帧解码器（`packages/rpc/src/frame-bytes`）跨块时不再逐块 streaming decode 再 `join`，改成按 chunk 存字节视图、换行时解一次；信封仍在 `\x1f` 到达时就 parse（Host 只用它做路由），因此大帧只解一次 UTF-8、不多做一次全文拷贝。8MB 单帧从 14.0–14.3ms 降到 5.9–6.2ms（×2.2–2.4），小帧与整页 JSON 数组两种语料持平 —— 后者的耗时全在 `JSON.parse` 上，不在解码。
- **钉住**：`reducer.test.ts` 新增一条用例，断言 `materialize` 之后只有被覆盖的那一帧换了引用、其余帧逐一同引用、`turnIndex` 原样复用（这条一红就说明有人把全表遍历加回来了）。

- **授权管理页接上**：`features/policy` 的方法名按事实归属改名 —— `policy.grants` → `policy.grants.list`、`policy.revoke` → `policy.grants.revoke`（记录是产品事实，撤销是产品动作，都不属于某一次工具执行）。设置页入口早已贡献（`settingsPages` 的 `policy.grants`，`SETTINGS_GROUPS.system`），之前缺的只是可用的方法名。顺带修掉页面一个真缺陷：刷新列表时会把「这条授权已经不存在了」的说明一并清掉，等于什么都没告诉用户 —— 现在 `load` 只管列表，清提示由发起动作的那一侧负责。
- **策略裁决统一进审计**：`policy.check` 成为裁决 + 会话放行覆盖 + 写 Journal 的唯一入口（引擎钩子与 RPC 走同一条），`PolicyService.check()` 把它交给 `apps/core/src/serve.ts`。放行 / 询问 / 拒绝、发放放行、撤销放行三件事都落 `policy.decided` / `policy.granted` / `policy.revoked`；审计写失败只记 warn，不让「记不上」变成「用不了」。`policy.decided` 补 `risk` / `workspaceRoot` / `toolCallId` 三个字段（只增不改，schema 版本仍为 1）。
- **在 HEAD 上修掉两个启动阻断（都不是本轮引入的）**：①`features/policy/src/core/index.ts` 的 handler 解构了契约里没有的 `sessionKey`，`typecheck` 直接红；②`policy` 声明依赖 `journal`，但两者都登记在第 1 级，内核 `assertTierOrder` 在真机启动时直接拒绝装配（`kernel.module_graph_invalid`，界面只报「引擎启动失败」）。**后者是闸门漏网**：`createCoreHarness` 只装被测模块、不带描述符，所以单测全绿。`policy` 升到第 2 级（它读 Journal、依赖 settings，比 journal 高一级是对的），并补 `apps/core/src/__tests__/assembly.test.ts` —— 用**真实装配清单**校验「一模块一描述符 + 依赖级别严格更低」，并真的把内核拉到 `core.ready`。两条断言都做过「把 tier 改回 1 → 变红」的反向验证。
- **网络出口规则层**：`PolicyContext` 增加 `url`；`networkDecision` 按「预设先关门 → 目标能解析才谈规则 → 白名单先于预设放行」判定，规则码 `network.allowlist` / `network.not_allowlisted` / `network.unparsed` 是稳定契约，命中的规则名与主机名单独放进 `PolicyDecision.network`（`NetworkVerdict`），审批卡片与审计不必再从 reason 里猜。`hostMatches` 按标签边界匹配（`evil-example.com` 不命中 `example.com`），只认 http(s)。`serve.ts` 的 `policyContextOf` 从 `url` / `target` / `href` / `endpoint` 取第一个像 http(s) 的目标。**真强制（经本地代理执行）仍未做**：这里只裁决，不拦流量 —— 与 §13.3 的「注入代理环境变量」是两件事，后者要等 Worker 环境注入口。
- **审计查询按工具 / 风险 / 工作区**：`journal` 服务新增跨线程 `query(types, { threadId?, fields?, limit? })`，过滤在 SQL 里做（`json_extract`，字段名来自调用方的固定清单、值走占位符）；`audit.query` 的 `threadId` 改为可选（不给就是跨线程），新增 `tool` / `risk` / `workspaceRoot`。字段条件与类别取交集：给了 `risk` 就不会把没有这个字段的审批事件带出来。跨线程结果按发生时刻排序 —— `seq` 只在一条线程里可比。

### 定时任务的提交不再冒充人话（2026-11-19）

真机现象：一条自动化线程里出现「【定时任务】自检-临时-可删-已改名 · 手动运行…」这样一条**用户气泡**，
下面挂「提交未完成；请先核对会话。」与「取回文字」。dev 库证据：该线程唯一一条提交 `status=failed`、
`error_code=submit_cancelled`、`error_message` 与码一字不差；提交与失败同一毫秒，omp 会话 147 ms 后才打开，
落地文件只有 6 行会话头、没有一轮。

- **提交记得住来历**（`SubmissionView.origin` / `conversation_submissions.origin`，迁移 v2 追加、老行默认 `user`）：
  定时任务经 `ConversationService.submit({ origin: 'automation' })` 投进去的那段话不再是「人打的一句」。
  界面对它的处理三处一致 —— 不画用户气泡（`withSubmissionRows`）、不进「取回文字」（`readFailedSubmissionText`）、
  不参与首句自动起名（`SubmissionService.submit` 只在 `origin === 'user'` 时调 `autoTitle`）。
  原来的样子是把内部抬头直接塞进人的输入框。
- **码不再当文案**：`SubmissionErrorCode` 是契约，给人看的那句话收进 `product-model` 的 `submissionErrorText`
  （`conversation.submit_cancelled` → 「这句话已停止」），两处收口（`cancelUnhanded`、`recoverOnStart`）与
  `event-router` 的 `settleUnstarted` 一并改。此前任务运行记录里会出现「没能开始运行：conversation.submit_cancelled」。
- **先复查再开会话**：`deliver()` 原先在 `acquireSession` 之后才看这一句还在不在，被取消的提交照样开出一条
  没有轮的空会话并落盘（真机证据里那份 6 行会话文件就是它）。现在开会话前先 `stillWanted`，抽成 `openSession`。
- **真正的堵点：只读档占着写租约**（2026-11-19 第二次真机）。第二次复现：自动化线程的提交 21:48:46 建好后
  `status=pending` 再没动过，会话文件只有会话头，`run` 永远 `running`，21:50 那次被跳过。
  根因在 `acquireWriteLease`：它不判姿态，只读档的定时任务照样去抢工作区写租约并**静默排队等**
  （最长 15 分钟）。只读档不写工作区，这个租约对它毫无意义，却把同工作区里所有真正要写的对话堵在后面。
  现在只读档直接放行（`posture === 'read-only' → return true`），不占也不等；`requireThread` 端口补 `posture`。
- **自动化那一轮必须看得见**：上一版把 `origin === 'automation'` 的提交行整条藏掉，结果那条对话是一片空白 ——
  人分不清「任务没跑」和「跑完了没说话」。现在改成**居中的系统条**（`UserMessageItem.automation`）：
  `turns.submit` / `SubmitInput` / `LiveProjector.userTurn` 把 `origin` 一路带到引擎，轮头来源写成
  `origin.kind === 'cron'`，投影据此成行、行组件画成系统条。条上的文字取**人写在任务里的指令**
  （去掉「【定时任务】…」抬头与 `automation_report` 那段交代），不取内部信封。
- **线程名字就是任务名**：从前标题拼「定时任务：<标题> MM-DD HH:mm」，两截都是噪音 ——
  侧栏那一行已有闹钟图标，时间戳只在同一天多次运行时有用却让每个名字都长成内部格式。现在直接用任务名。
- **协议**：`turns.submit` 参数增可选 `origin`，`PROTOCOL_VERSION` 75→76，快照已重生成。
- **验证**：`typecheck`、`format:check`、`lint`（含 depcruise、style-boundaries、ratchet 之外的各闸门）通过；
  新增用例三条（automation 提交不画气泡也不进取回文字 / 不调 autoTitle、取消与重启落库的是中文文案）；
  `features/conversation` 与 `features/runs` 共 230 条用例全绿。

### 写租约排队 + 策略门按会话路由（2026-11-16）

真机故障：完全访问的一条对话还在跑时，另外新开三条对话（只读 / 请求批准 / 帮我批准各一条）各发一句话，
三句全部**当场**收成 `workspaces.write_busy` —— 既没交给 omp（屏幕上没有回复、没有时间线），又只剩
「提交未完成；请先核对会话。」。dev 库里的证据是三条失败提交 `error_code=workspaces.write_busy`、
omp 会话文件只写了一个空会话头，同一窗口里三条线程的 Journal 却各有一条 `policy.decided action=ask`。

- **租约冲突改为排队**（`SubmissionService.acquireWriteLease`）：§14.4 限的是**并发写**，不是这一句话的
  生死。别人的写轮占着工作区时等它收口（`releaseWriteLease` 按工作区叫醒 + 5 秒兜底节拍重判），
  等到了自己往下交。等待有两个上限：15 分钟超时才收成 `workspaces.write_busy`（持有者永远不收口的兜底），
  等待期间被停止 / 丢弃则整句不再交出。为此把 `handed` 标记挪到真正交接之后 —— 从前它记在拿租约之前，
  于是「还在等」的那一句对 `turns.cancel` 已经不可见了。
- **策略门按会话精确路由**（`policyGateFor`）：从前只按 cwd 取「最严格的门」，同一工作区里完全访问的线程
  会被只读 / 询问线程的门拦住，审批卡片还会在另一条对话里冒出来（同一份 Journal 证据：正在跑的
  full-access 线程没有任何 ask，三条**还没交给引擎**的线程却各有一条 ask）。现在主会话按 omp 会话号命中
  自己的门，子代理按会话头的 `parentSession` 落回父线程，认不出的会话才退回「最严格 + 最近建的门」。
  这条同时结掉 2026-11-14 那条「同一 cwd 多个线程不同档位时子代理会落到最严格的门」的待决问题。
- **验证**：`typecheck`、`format:check`、`lint`、全量 `bun test` 3315 通过 / 1 跳过 / 0 失败；
  新增租约三条（排队后交出 / 等待期间被停止 / 超时收成 write_busy）与策略门路由一条（含 dispose 后摘号）。

### 2026-11-03 WorkBuddy 反代对齐 magpie 网关（第二轮）

与 `.scratch/magpie-src`（HEAD `59fdab0`）逐条对照后的补齐。协议层本来就移植得扎实，这一轮动的是**网关与路由**这两层：上一版只学了「四类固定休息时长」，magpie 真正的中枢——失败即休息 + 分层放行 + 按额度/到期排序——没学到。五项审计的完整对照（含判定与证据）在 `.scratch/wb-audit/`（gitignore）。

- **「全在冷却」不再是 401**：`proxyAccounts` 过去把休息中的号全滤掉，反代于是回 `401 not_signed_in`——omp 把 401 当凭据坏了（pi-ai 的 `Flag.AuthFailed`，且是它唯一 `retriable=false` 的分支），用户会去重登一个没坏的号。现在照 magpie 的 `restLast` / `probeOne` / `quotaHeld` 分三层：休息的排最后但**留在名单里**；全都歇着时每分钟放「最快回来的那一个」当探针；真的一个可用都没有才回 `429 all_accounts_resting` + `Retry-After`（真·没有账号仍是 401）。
- **失败分类补上「未知」这一类**：`kindOf` 过去只认 401 / 403 受限 / 429 / 400 额度，其余（5xx、408、没归类的 4xx）当作「请求本身有问题」**当场交回**、不换号也不休息。现在按 magpie 的 `failOther` 换下一个账号，并给这个号自己的阶梯：1 分钟起翻倍，封顶 10 分钟（magpie 的 `longestRetry`）。
- **休息阶梯会回落了**：新增 `REST_FORGET_MS`（30 分钟遗忘窗，magpie 的 `rateForget`）与 `onAccountAnswered`——**任何一次成功应答都清零**（magpie 的 `served`）。此前只在换令牌 / 重登时清，于是偶发一次限流会被单调放大到 30 分钟并长期停摆。
- **上游写了「何时恢复」就用它**：WorkBuddy 的 429 正文带「将在 2026-11-02 19:17:02 UTC+8 重置」（插件的 `windowReset` 早就会解析，只是一直只喂积分卡片）。反代现在从错误体里读出 `resetAt`，Core 按它休息，上下限 [1 分钟, 7 天]。omp 自己读不出中文这条（它的正则要求「将在 ⟨时间⟩ 重置」紧邻，`UTC+8` 夹在中间），所以只能我们读。
- **短休息不再覆盖长休息**：`setRest` 改成取 `max`——一次一小时的受限休息不该被紧接着的一条 429 改成 1 分钟（magpie #3289 的同一判断）。
- **受限与「渠道拒绝」分开了**：`RESTRICTED` 正则去掉裸 `permission_error`（插件把 11128 渠道拒绝也写成这个 type，只要落在 403 上就让账号白歇 2 小时），改为先读结构化 `error.code === 11140`，正则只作兜底，并补上繁体「帳號存在異常行為」。
- **客户端取消失不算上游故障**：abort 时直接回 499、不换号、不记失败（magpie 的 `failCanceled`）。此前会「先记一条上游失败、再打第二个号、最后回 502」。
- **选号接上额度**：`orderedRecords` 过去只有「休息排尾 → 非过期 → 首选 → created_at」。现在照 magpie 的 `Smart`：用量分档（90% / 98% 之后的两档）→ 积分到期时刻（`runsOutAt`，数据早就有了，此前只喂界面那行「N 积分即将到期」）→ 已用比例 → 首选 → 创建时间。**首选从「无条件置顶」降为同分 tiebreak**，否则多账号等于单账号；`snapshot` 里「首选失效就取 `records[0]`」的静默回落也去掉了（徽标不再偷偷飘到别的号上）。
- **流形状按 Chat 契约修缮**（对应 magpie 的 `chattidy.go`）：WorkBuddy 的 SSE 每个 delta 都带 `"tool_calls": []`、思考结束后带空 `reasoning_content`、未终结帧的 `finish_reason` 是空串、纯文本末帧还带空的 legacy `function_call`。omp 现在扛得住（空数组有 `length > 0` 判断），但空 `finish_reason` 正好落在 `else if` 的 falsy 分支上——客户端一升级收紧类型就会在同一处爆。插件 `finish()` 里加一层 `tidied`（只走 chat，Messages 不动）。
- **会话身份接上了**：插件有完整的会话管线，但唯一写入点 `chat.headers` 钩子**全仓无调用者**，于是会话 id 一直退化成「首条用户消息摘要 + 每进程随机 SALT」，Core 一重启就换会话。现在 `CustomProviderDef` 多一格 `sessionHeader` → models.yml 的 `compat.promptCacheSessionHeader: x-conversation-id`（omp 只在有会话 id 时才发），反代把它转成插件的内部会话头。
- **回复头收拾干净**：cookie / `www-authenticate` / 缓存与跳转一类不再漏给 omp（照 magpie 的 `replyheaders.go` 拒绝名单）；绘图端点回一句中文可读的 400，不再是裸 404。
- **休息对用户可见**：`WorkBuddyAccount` 加 `restUntil` / `restReason`，设置页显示「冷却中 · N 分钟后重试」与原因。契约形状变了，`PROTOCOL_VERSION` 53 → 54；已装好的 Core 必须重新构建（`bun run core:build`）。
- **不做的**（理由见 `.scratch/wb-audit/`）：MaxRPM（动机是 OpenRouter 的 20 RPM，WorkBuddy 是按天窗口）、MaxAccounts（动机是出口 IP 被封，本地反代不适用）、模型级休息（要新表、要按模型过滤，收益只在「免费模型窗口满、付费模型还能用」这一种情形，先记为待办）、per-account 并发闸门（omp 子代理默认 32 路，值得补，见待决问题）。

### 2026-11-03 WorkBuddy 缓存命中率与会话亲和（第三轮）

用户问「缓存命中率为什么这么低」。三份只读审计（数据通路 / 会话身份与黏号 / 请求体前缀稳定性）在 `.scratch/wb-cache-audit/`（gitignore），汇总见那里的 `00-summary.md`。

**结论先纠正前提：命中率不低。** 旧路径（经外部 magpie 网关）加权 **99.14%**（release 3579 次请求），97.8% 的请求本身 ≥90%；266 轮的会话里 `cacheRead` 跌破上一轮 prompt 90% 只发生 1 次。用户看到的低值来自**面板口径**：`cacheHitRate = cacheRead/(input+cacheRead+cacheWrite)` 的分母与 omp 的 `calculatePromptTokens` 完全一致（不是 bug），但它取的是 `sessionManager.getUsageStatistics()` 的**会话累计**，含首条消息的冷启动。一条 8 请求里 3 条 0%（首条 + 隔 84 分钟 + 隔 21 小时）的会话显示 61.9%。按空闲间隔分桶：<1min 97.1%（n=4499）、1–5min 94.4%、5–15min 86.2%、>60min≈0 —— 上游是「内容前缀 + 短 TTL」，不是我们丢了缓存。`cache_write` 全库恒 0 也是上游只发 `prompt_tokens_details.cached_tokens` 的结构性结果（pi-ai 对 DeepSeek 形态显式置 0），不是丢数据。

这一轮改的是审计里**真正值钱的那一层**：

- **会话黏号（P0，magpie 的 affinity）**：选号原本**每个 HTTP 请求**重算一次（`proxy.ts` 的 `accounts()`），于是一轮工具循环里某个号失败一次就搬家，上游为这个会话攒的前缀缓存全作废。现在反代把 `x-conversation-id` 抽成 `sessionKeyOf()` 只读一次，同时喂给选号、上游头和成功回调；Core 侧加一张「会话 → 上次答出来的号」的内存表（`STICK_TTL_MS` 5 分钟 = magpie 的 `cacheCold`，`STICK_MAX` 512 = `sticksKept`），命中且该号**仍可交付**（未休息、非 expired、通道建得起来）时提到第一位，其余仍按 `orderedRecords` 补齐。**它只是排序提示不是锁**：钉住的号这次失败仍换下一个；不可交付时该号仍按原序参与名单（不凭空消失）。写入时按条数淘汰最旧，`dispose` 里清空 —— Core 是长期进程，TTL 只在读的时候清，只写不删就是泄漏。
- **面板口径说明（P1）**：命中率那一行的 label 受基准截图约束不能动，改挂原生 `title` 说清是「本会话累计」、新会话或久置后偏低是正常的。算法与数字一字未改。
- **逗号预置（P1，前缀稳定性）**：`systemOn` 里在 `developer → system` 之后调 `commaPausedOn(b)`，让 OPENERS 的逗号**第一轮就加好**，不再等被拒一次由 `commaSystems` 学会。学会那一轮 `messages[0]` 中途变形，实测共同前缀只剩 15.3%（另量法 10.8%），而且那个 Set 只在进程内存里，Core 每次重启都要重学。预置后第 1→2 轮共同前缀 57.3%，已与「完全不改写」的下界 57.2% 持平。**预置与 400 兜底必须走同一个函数**（`commaPausedOn` 的 `roles` 改成可选），否则两条路径各产一种形态、每轮翻一次比不预置更糟；`opened()` 的幂等由 `opener.test.ts` 钉住。
- **选号读 aside 积分的真实消耗（P1）**：`rankOf` 过去把 `aside` 窗口全过滤（原注释「只是摆着看」），而 WorkBuddy 的真实消耗正记在 aside 那格：非 aside 的 `Credits` 是套餐额度（实测 `used` 恒 0），在烧的是 aside 的 `Extra credits`（实测 43.13/7105）。于是「剩余额度」这一维长期为 0，排序退化成只比到期日。现在 `used` 与 `lapse` 取所有窗口（含 aside），**tier 仍只按非 aside 分档** —— 90%/98% 说的是「套餐快用完了」，aside 不决定账号停不停，不该把它推进 low/spent。契约注释里 aside 的语义（「另一格才决定账号停不停」）说的是**停不停**，不是**排序**，两者互不冲突。
- **不做的（P2，本轮未动）**：SALT 持久化（插件 `idFor` 每进程随机，导致发给上游的 `X-Conversation-ID` 每次重启都变；对命中率的影响未验证 —— 首条消息就有 62.8%/85.4% 命中说明上游不按 id 分区，确定代价在会话分组与可观测性）、黏号落盘（`affinity.json` 的等价物）、`/fresh` 挡掉、`prompt_cache_key` 试验。

**未验证、不要当结论用**：① 直连路径只有 10 条样本且全是短会话，长会话稳态命中率无法判断；② 旧库 14 条超长 prompt（>300K）的缓存坍塌（折全局 0.35pp）是上游挤掉还是插件改写前缀分辨不出；③ 两个号之间前缀缓存是否按账号隔离；④ WorkBuddy 是否认 body 里的 `prompt_cache_key`。判定实验写在 `.scratch/wb-cache-audit/00-summary.md` §五。

### 审查面板的统计只有一份来源（2026-11-01）

- **症状**：展开一个文件的 diff 前后，卡头与工具条的 `+N −M` 会变；新增几百行的文件显示 `+0`；打开多个文件后拖动分隔条或敲提交信息明显卡。
- **根因（统计）**：清单 `git.review` 与按需补丁 `git.filePatch` 各自给出一套加减数，补齐时整份 `DiffFile` 被补丁覆盖，而总账要等下一次 `project()` 才重算 —— 同一屏上出现三份口径。刷新时 `project()` 又优先复用上一趟的旧条目，新清单的统计被丢掉（空文件先出现一次 `+0`，之后就一直冻结在 `+0`）；补丁缓存的身份原本由旧缓存自己的 `stat` 反推，内容变了而净增行数恰好相同时认不出来。
- **裁决**：统计与处境只认清单（`git.review`），补丁只补行带（`rows`），`binary` 也以清单为准。缓存身份改成「清单的读取代次 + 影响问法的开关」，不再从补丁正文反推。这样卡头、总账、Git 工具格与撤销账本是同一组数，展开与折叠不再改变任何数字。
- **根因（性能）**：`ReviewPane` 订阅整份 store，`Card` / `Body` 没有记忆化 —— 草稿每敲一键、分隔条每拖一帧、任一文件解析完成都会重画全部卡的整棵行带。`content-visibility` 只省布局与绘制，省不掉 React 计算。
- **裁决**：`Card` 收紧到只依赖自己那一份（`file` / `open` / `openGaps` / `wrap` / 两个稳定回调），`Tree` 的行表按路径与折叠态记忆化。既有虚拟化（潜在行 > 500 走 `VirtualRows`）、按需取补丁与串行排空都不动 —— 那是已经正确的设计，本次不重写。
- **留下未改**：`enrich` 仍是串行（一次一份文件），收益只限已打开的那几份，改并发要另做有界池与顺序测试，本次不动。

### 换肤与换面的补间（2026-10-26）

- **为什么加**：主题切换与设置页 / 右坞换内容原本是硬切，一帧跳完。Electron 45 的 Chromium 156 有 View Transition API，React 19.3 也有 `<ViewTransition>`，不必引第三方动画库。
- **不用 React 的 `<ViewTransition>`**：它只在 `startTransition` / Suspense / Action 这类异步更新时触发，`navigation` 与 `layout` 都只是普通 Observable 的同步 `set`；要让它生效得把路由与坞的写入全部改成 transition，等于为一帧补间改动调度语义。走 `document.startViewTransition` 直接套在写入外面，语义不变。
- **`flushSync` 是硬需求**：`update` 回调返回时浏览器就拍新快照；Observable 的 `set` 只触发 React 重渲染并排队，不 flush 的话新图还是旧的，补出来是同一张脸。已在 `withViewTransition` 里统一 flush，调用方不必记这条。
- **减弱动效要自己判**：`tokens/accessibility.css` 那条全局 `*` 规则只覆盖元素树，`::view-transition-*` 是伪元素树、压不到。helper 里判系统偏好与 `data-reduce-motion` 两处，任一成立就直接同步落地、不进快照；CSS 里那份 `::view-transition-*` 规则是第二道闸（防将来有人绕过 helper）。
- **不换库的判断**：`animated-rows`（FLIP）继续手写 WAAPI —— 它必须在提交前量旧位置、提交后量新位置，任何声明式库都会多一层帧时序风险；`ticker-engine` 继续自研 rAF —— 它要按速度积分做减速滑行。两处都不在本次范围内。
- **捕捉范围**：换肤不点名，整窗淡一次是对的；换路由只给主区那张卡名字（页头、侧栏不跟着呼吸）；坞里换格只给内容块名字。三处都先把 root 的 `view-transition-name` 摘掉，否则整棵树仍会被拍成一张图、与局部那张叠成两层淡入。
- **核验**：Electron 45 真实 Chromium 里量到 `startViewTransition` 可用、时长读到 `--ui-duration-normal`（0.18s）、`:active-view-transition` 命中、update 内 DOM 落地、减弱动效两条（系统偏好 / 外观开关）均同步不建过渡、换肤走过渡且同值不重复。

### Core 产物完整性（2026-10-26）

- manifest 不能由「实际生成的子集」定义完整性。构建与校验共用固定必需产物清单，缺少必需的 Windows natives 就失败。必需清单以**上游实际发布的文件**为准：`@oh-my-pi/pi-natives-win32-x64@18.12.6` 只随包发布 `baseline.node`（其 `package.json` 的 `main` 也指向它），因此 `baseline` 是必需项；`modern.node` 是可选增强，上游若带上就一并复制并纳入哈希，绝不伪造不存在的文件。全部哈希都对只代表静态完整性，运行是否可用仍由 Windows probe 验收。Linux 的默认安装不带 Windows 可选依赖时，构建失败是正确行为，不能降级成可发布产物。

**legacy-pi 空注册表**：omp 的 `legacy-pi-compat.ts` 里有一句字面量 `import('omp-legacy-pi-modules')`，那是它自己 monorepo 的构建插件（`scripts/legacy-pi-virtual-module.ts`）注入的虚拟模块，用来把旧 scope（`@mariozechner/pi-*` 等）的扩展 import 重定向到宿主内已打包的实例。Poietica 不加载用户扩展（会话走 `disableExtensionDiscovery`），不需要那张注册表，但那一句在依赖图里是静态可见的，不解析就整个 Core 构建失败。所以构建脚本固定注入一个空注册表（`BUNDLED_PI_MODULE_LOADERS = {}`），**不再尝试调用官方插件**：它扫 `<包>/../../packages/<pkg>/package.json`，npm 安装形态里没有那一级，必然 ENOENT。manifest 里的 `legacyPiPlugin` 字段随之删除 —— 它只描述那次注定失败的尝试。

**omp 文档索引静默留空**：`PI_DOCS_EMBED` 的生成器同样读 `<包>/../../docs`，npm 安装形态下必然 ENOENT。空串是**正确取值**而非降级：omp 的 `docs-index.ts` 见到空串就回退到随包的 `dist/docs-index.generated.txt`（发布包自带），`omp://` 文档照常可读。构建脚本因此静默吞掉这条 ENOENT、不留日志 —— 每次构建刷一条注定失败且无害的警告，只会训练人忽略构建输出。

### 功能生命周期边界（2026-10-26）

- UI 的失败隔离必须回收已注册资源，而不只是记一条 failures；服务注册表增加永久撤销作用域，UI 按功能持有资源并阻止失败依赖继续启动。不支持同一注册表内热重装，重启内核会创建新注册表。
- Core ready 增加协作式取消 signal：内核只保证旧钩子链不继续调度；功能内部的 await / RPC / 写状态仍由功能校验有效期。workspaces 的名单刷新接入 signal 和请求序号，conversation 的多步恢复接入步间检查；不声称所有异步入口已完成迁移。

- **`agent_end` 非终态**：`isTerminal === false` 是排程暂停（retry / compaction continuation / stop-time reminders / queued input），此时收轮会让下一段输出落进已关掉的轮。改为非终态一律不收轮（`awaitingAsyncWork` 那一档也一样 —— omp 只把标题置 idle，run 本身还在等后台作业），读数与异常账照旧结清；另外照 omp 自己的 `#finishWhenRunSettles` 补了一条看门狗 —— 终态 `agent_end` 并不保证会来（abort 能把排好的重试 / 压缩续跑取消在 `agent_start` 之前），所以非终态 settle 之后等 `waitForIdle` + `settleAsyncWork`，会话真的静下来（无后台活、无 admitted 提交、队列为空）就收轮，新一轮的 `agent_start` 会换代作废它（`event-pump.test.ts` E11–E14 钉住）。
