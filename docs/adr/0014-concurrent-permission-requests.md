# 0014 · 一轮里可以同时挂着几个权限请求

## 背景

ADR 0013 把权限处理器移出 ACP 派发循环之后，一条不变式随之失效：

> At most one: the agent waits for an answer before asking anything else.

这句话此前写在 `timeline-queries.ts` 里，但它从来不是协议给的保证。它成立，
只是因为我们自己堵住了派发 —— agent 的第二个请求进不来。堵塞一拆，Kimi 的
`Agent` 工具并行派出的每个子代理都会各自要一次审批，几个请求同时在飞是常态。

原生侧本来就是复数的：`desk.rs` 持有 `HashMap<String, Waiting>`，并提供
`waiting()` 与 `abandon(&[String])`。单数的只有客户端这一侧。

## 决定一 · 交出本段最早那个未答复的请求

判据从「反向扫，命中即返回」改成「反向扫，记住最早的那一个」。仍是一趟扫描、
仍在段边界收手、仍不分配。

交出最晚那一个的后果不是「顺序不好看」，是先问的那几个永远拿不到按钮：它们的
`oneshot` 收不到 `answer()`，工具卡片停在 `in_progress`，这一轮再也结束不了。

## 决定二 · 一次只交一个，面板不改成队列

并行的请求彼此独立，一个个答与一叠一起答在协议上没有分别。一个个答不需要新的
UI，也不需要新的状态。答掉一个，下一个顶上来。

待到确有需要显示「还有几个」时，`PermissionItem` 本来就按 `requestId` 记身份，
多条共存不需要数据层改动 —— 那时再加，也不必先埋一层。

## 决定三 · 「还有没有人在等」与「该问谁」是同一个判据

投影层在 `permission_resolved` 上要判断这一段是否还有未答复的请求，那与选择器
问的是同一件事。所以只有一份实现（`pendingPermission`），投影层是它的第二个
读者 —— 与 `renderable.ts` 里那条既有规矩同形：抄成两份就会有两种「还在等」。

函数因此去掉 `select` 前缀：它也跑在写入路径上，那里不是在选要渲染的东西。
旧名全仓改掉，不留转发壳。

## 决定四 · `permission_resolved` 不再无条件写 `running`

第一个答复到达时若把状态放开，`selectIsBusy` 就说这一轮不在等人了，而其余请求
还挂在原生侧的桌子上，界面上再没有入口。状态在落账之后按实际情况收口。

## 未采纳

- **给每张卡片加取消按钮**：ACP 没有针对单次工具调用的取消，只有 `session/cancel`。
- **把子代理画成父子树**：协议在两次工具调用之间没有任何父子字段，画出来就是编的。
- **客户端自建风险分级**：那条 19 节点的责任链跑在 agent 侧，客户端拿不到它的输入
  （工具申报的资源访问、git worktree 判断）。到达客户端的请求，已经是链判成 ask 的
  那一部分 —— 再判一次只会与上游不一致，且每接一家 agent 就多一份不一致。
