# 0015 · 审批住在输入框上，答完不留痕

## 背景

审批此前是转录里的一张卡：请求态一张，答复之后换成一张结果卡。两件事因此都发生在
一条会滚动的流里。

## 决定一 · 审批带在输入框正上方，与它咬合

一次审批是拦在「继续」前面的一道闸，闸属于操作区。放在流里，它会随滚动离开视野，
人得先找回它才能放行。带子住在 `.assistant-surface__dock` —— 那一带本来就跨两个
相位、本来就被 `useDockClearance` 实测高度写进 `--cp-dock-clearance`，所以转录末端
的让位是白拿的，没有新增管线。

输入框自身不改：带子只画上面两个角，下边不画（那条边输入框已经画过）。

## 决定二 · 答复之后什么都不留

转录记的是「发生了什么」，审批记的是「我当时点了什么」——后者是操作痕迹。原生侧的
`permission_requested` / `permission_resolved` 一条不少地记着，那份日志才是权威。
屏幕上再留一张卡片，就是第二个事实来源。

代价已知并接受：回放旧对话时，看得出某条命令没跑成，看不出是被人拒的还是工具自己
报的错。不为此加任何标记。

## 决定三 · 「提问用户」不在此列

它在协议上也是一条 permission，借的是同一条通道，但它不是审批：agent 问的是一个
选择，答案是对话的一部分。所以它答完之后仍然留在流里。

判据不能下沉到 `agent-timeline`：认不认得出一道提问取决于对面那家 agent 的说法
（`dialect.questions`），那是 UI 的知识。因此 `renderable.ts` 的「哪一条上屏」一个字
不动，例外写在 `PermissionRecord` 这一支里。

## 决定四 · 一次一个，序号只报分母

并行请求彼此独立，一个个答与一叠一起答在协议上没有分别，而一个个答不需要把带子改成
队列。恒定交出最早那一个（ADR 0014），所以分子永远是 1。

## 未采纳

- **队列面板**：把 n 个请求同时铺开。协议不要求，而它会把一条控件长成一块内容。
- **展开长命令**：带子长高会推动输入框，而输入框的位置是打字时唯一的锚。要读全文
  去工具卡。
- **客户端风险分级**：见 ADR 0014 —— 到得了 ACP 的请求，已经是 agent 那条策略链
  判完之后剩下的 `ask`。
